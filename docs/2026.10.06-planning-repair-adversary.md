## ADV-REPAIR-001 — legacy numbered review requires an undocumented plan ID

Severity: P2. Affected capability: maintained planning preparation on every host using the shared implementation.

The previous planning-flow contract requires saving mapping, mappingBinding and local date. It does not require a planId on numbered review state. The new planning-flow reference explicitly promises that an existing same-day `planning-review.json` is reused without discarding its numbers. However `lib/planning/session.mjs`, at the saved review guard, requires `saved.planId === current.id` even for legacy review state.

Concrete reproduction: create a valid current plan and configured fixture vault, prepare its binding, and save legacy `planning-review.json` containing `{date:'2026.10.06', mappingBinding:<actual binding>, mapping:{<valid task UUID>:17}}`. Calling preparation throws `Saved review belongs to another date, plan or vault; recover it before reusing numbers`. No mismatched date, vault or explicit plan ID exists; the field simply was not part of the earlier required persistence shape.

Retained probe: `.temp/plugin-review/repair/probe.mjs`; observed legacy result: `.temp/plugin-review/repair/legacy-result.json`. Run `node .temp/plugin-review/repair/probe.mjs` from the repository root.

Acceptance: a same-day same-vault legacy mapping lacking planId should retain its existing handle and safely acquire the actual plan ID on verified save, or provide an explicit supported migration preserving the mapping. Explicit foreign date/binding/planId values must continue to reject. A legacy review must never silently regenerate or reinterpret its numbers.
