# UC-00.03.01 Authorize Read-Only Communication Account

## Actor

Individual user connecting an email or team chat account to surface incoming updates during daily planning.

## Goal

Authorize read-only access to email or chat messages and track incremental fetch checkpoints while keeping credentials protected and never sending outbound messages.

## Starting Context

The user has configured their workspace ([UC-00.01.01](../f-00.01/uc-00.01.01-setup-workspace-and-templates.md)) and wants incoming messages to be analyzed for task and blocker updates during [C-04: Three-Screen Planning Session Macro-Flow](../../concepts/c-04-three-screen-planning-session.md).

## Entry Route

The user initiates communication account sign-in during setup or before starting a daily planning session with email or chat integration enabled.

## Trigger

The user requests communication account sign-in or enables a communication source for daily planning.

## Process

```text
User authorizes read-only communication access
+-- Starting context: Workspace is configured and user has client credentials for email or chat
+-- Entry route: User invokes communication sign-in or enables a message source
+-- Trigger: User starts the authorization flow
+-- Step 1: System verifies that required client credentials are provided
|   +-- Credentials present: System opens the read-only authorization prompt for the user
|   \-- Credentials missing: System explains which credential setting is needed and stops cleanly
+-- Step 2: User approves read-only access in the provider sign-in prompt
|   +-- User grants approval: System receives and seals the authorization token in protected storage
|   \-- User cancels or provider rejects sign-in: System reports sign-in failure without exposing secret values
+-- Step 3: System initializes the incremental fetch checkpoint for the connected source
\-- Success: Communication source is ready to fetch unread messages in read-only mode during planning sessions
```

## Step Details

### Step 2: User approves read-only access in the provider sign-in prompt

Only read-only permission is requested so the system can never send, draft, or delete messages. Access tokens and refresh secrets are masked in all status messages and diagnostic output.

## Success

The communication account is connected with strictly read-only permission, credentials are sealed without plaintext exposure, and incremental fetch tracking is ready for the next planning session.

## Failure Cases

- Missing client credentials: The user receives a clear message stating which credential must be configured before sign-in can begin.
- Rejected or timed-out authorization: Sign-in aborts cleanly with an explanation, never printing partial tokens or secrets.
- One communication source unavailable during planning: The failing source is noted on the planning screen while remaining sources and local planning continue uninterrupted.
