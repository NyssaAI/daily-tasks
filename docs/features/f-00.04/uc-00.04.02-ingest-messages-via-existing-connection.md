# UC-00.04.02 Ingest Messages Through Existing Assistant Connection Using Shared Checkpoints

## Actor

Individual user starting a daily planning session with an existing assistant email or chat connection enabled.

## Goal

Pull unread or new messages through the assistant's existing email or chat connection—bounded to the configured initial lookback window (7 days by default) on the first pull and to the saved checkpoint on every subsequent pull—and receive the exact same correlated update suggestions and checkpoint advancement on Screen 1 and Screen 3.

## Starting Context

The user has selected an existing assistant connection and an initial lookback window (defaulting to 7 days) during setup ([UC-00.04.01](uc-00.04.01-discover-connections-and-configure-lookback.md)) and starts a daily planning session ([C-04: Three-Screen Planning Session Macro-Flow](../../concepts/c-04-three-screen-planning-session.md)).

## Entry Route

The user asks the assistant to plan their day (or start a daily planning session) while an existing assistant communication connection is configured.

## Trigger

The user initiates a daily planning session.

## Process

```text
User plans the day with messages pulled from an existing assistant connection
+-- Starting context: Existing assistant email/chat connection is enabled in the user's setup
+-- Entry route: User asks to plan the day
+-- Trigger: Daily planning session starts Stage 0 message collection
+-- Step 1: System determines the fetch window for each enabled communication source
|   +-- Saved checkpoint exists for the source: System sets the fetch cutoff to the checkpoint timestamp and last message ID
|   \-- No checkpoint exists yet (first pull): System sets the fetch cutoff to the configured initial lookback (default 7 days)
+-- Step 2: Assistant reads incoming messages within the fetch window using the existing connection
|   +-- Connection returns messages: Assistant passes the read-only messages into the planning session
|   \-- Connection is unavailable or errors: System records the source error on Screen 1 and continues planning without blocking
+-- Step 3: System filters, correlates, and drafts suggestions using the shared pipeline
|   +-- System drops any message at or before the checkpoint (or older than the first-pull lookback cutoff)
|   +-- System links new messages to matching projects, tasks, and blockers and generates numbered Screen 1 suggestions
|   \-- System stages the updated source checkpoint for the newest ingested message
+-- Step 4: User adjudicates suggestions on Screen 1, assigns tasks on Screen 2, and confirms on Screen 3
|   +-- User confirms the daily plan: System writes the daily plan and saves the advanced checkpoint for the source
|   \-- User cancels the session: System leaves the previous checkpoint unchanged so messages are re-evaluated next session
\-- Success: Existing connection messages are correlated into the plan and the shared checkpoint advances cleanly
```

## Step Details

### Step 1: System determines the fetch window for each enabled communication source

Whether a source uses an existing assistant connection or a standalone connector, the same checkpoint store governs the time window. On the first run (when no checkpoint has been saved), the cutoff is calculated from the user's configured initial lookback window (no more than 7 days by default). On subsequent runs, the cutoff is the exact timestamp and last message identifier recorded in the saved checkpoint.

### Step 3: System filters, correlates, and drafts suggestions using the shared pipeline

Messages supplied through the assistant's existing connection go through the exact same deduplication, checkpoint boundary enforcement, task/project/blocker correlation, signal phrase detection, and Screen 1 suggestion numbering as messages from standalone connectors. The checkpoint only advances permanently when the user confirms the plan on Screen 3.

## Success

Messages from the user's existing assistant connection are bounded to at most 7 days (or the user's configured lookback) on the first pull, incrementally fetched from the saved checkpoint on subsequent pulls, presented as numbered update suggestions on Screen 1, and never fetched twice once the plan is confirmed.

## Failure Cases

- Existing assistant connection fails or times out during session start: Screen 1 displays a non-blocking status notice for that source while carried-forward tasks, other sources, and project planning proceed normally; the source's previous checkpoint remains intact.
- Messages returned outside the requested lookback or checkpoint window: The system deterministically filters out any message older than the first-pull lookback cutoff or at/before the saved checkpoint so out-of-window messages never generate noisy suggestions.
- Session is cancelled before Screen 3 confirmation: Staged checkpoint updates are discarded so unread messages are not lost and will be fetched again in the next session.
