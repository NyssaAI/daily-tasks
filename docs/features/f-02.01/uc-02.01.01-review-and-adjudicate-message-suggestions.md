# UC-02.01.01 Review and Adjudicate Message-Derived Suggestions on Screen 1

## Actor

Individual user starting a daily planning session with unread email or team chat messages.

## Goal

Review carried-forward daily selections alongside numbered update suggestions derived from incoming emails and chat messages, and explicitly accept, edit, or reject each suggestion.

## Starting Context

The user initiates a daily planning session (Stage 0 and Stage 1 of [C-04: Three-Screen Planning Session Macro-Flow](../../concepts/c-04-three-screen-planning-session.md)); unread messages from connected communication sources are fetched and correlated against open projects, tasks, and blockers.

## Entry Route

The user asks to plan the day (e.g., `"Let's plan the day"`), opening **Screen 1 (Plan the Day)**.

## Trigger

The planning session starts or refreshes Screen 1 after message correlation completes.

## Process

```text
User reviews Screen 1 and adjudicates message suggestions
+-- Starting context: State graph compiled from records; unread messages fetched and matched to open work
+-- Entry route: User starts daily planning session (Screen 1)
+-- Trigger: Screen 1 is displayed
+-- Step 1: System displays headline counts (open projects, open tasks, late tasks, blockers) and Current Plan rows (1..K)
|   +-- Message analysis still running: Screen notes that messages are still being analyzed while rows 1..K remain usable
|   \-- Message analysis complete: Screen displays Suggested Updates table with stable row numbers (K+1..N) and cited message sources
+-- Step 2: User inspects suggested new tasks, status changes, Definition of Done checks, and blocker updates
|   +-- User asks for details on a row (e.g., "Show details for 6"): System displays the full underlying source message
|   \-- User replies with batch verdicts by row number (e.g., "3 accept, 4 accept but due Friday, 7 reject")
+-- Step 3: System validates every verdict in the batch against the session state
|   +-- Valid verdicts: Accepted/edited changes are staged in the session, rejected items are logged, acted suggestions are pruned, and Screen 1 refreshes
|   \-- Invalid row number or bare number without verdict: System refuses the batch and asks for clarification without mutating state
\-- Success: User finishes desired Screen 1 updates and replies "yes" to proceed to Screen 2 (Project Review)
```

## Step Details

### Step 1: System displays headline counts and Current Plan rows

Current Plan rows keep their assigned row numbers (`1..K`) whether or not suggestions have finished loading. When suggestions appear, they receive the next sequential numbers (`K+1..N`) so earlier row numbers never change meaning.

### Step 3: System validates every verdict in the batch against the session state

Unanswered suggestions are never auto-applied; if the user moves on to Screen 2 with unanswered suggestions, those suggestions remain pending and their source messages remain unreviewed for the next session (see [C-03: Explicit Adjudication & Decision Log](../../concepts/c-03-explicit-adjudication-and-decision-log.md)).

## Success

All adjudicated suggestions are validated, staged in the session, and recorded in the decision log, while unanswered items remain safely pending as the user advances to Screen 2.

## Failure Cases

- Bare row numbers without `accept`, `reject`, or `edit`: System refuses the ambiguous reply and asks the user to specify the intended verdict.
- Out-of-range row number: System reports which row number is unknown on Screen 1 and leaves all suggestions unchanged.
- Failing communication source: Screen 1 reports the unavailable source inline and continues displaying suggestions from working sources and local records.
